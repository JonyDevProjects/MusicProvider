# testing-strategy
- When documenting completed testing/validation sessions, write a structured markdown report in `/docs/testing/` — include environment configuration, optimization results with evidence (logs/timings), an end-to-end user flow log, a validation checklist table, quick diagnostic commands, and technical notes (e.g., tunnel URLs, build mode caveats). Confidence: 0.85
- For Flutter multiplatform E2E tests: use the official `integration_test` package (not flutter driver) for iOS and Android, plus Playwright for the web target. Confidence: 0.90
- For Flutter web (CanvasKit) E2E with Playwright: verify values via `aria-label` on semantic nodes (`flt-semantics`), not via DOM text; expose durations on search results (`TrackResult-*`) since `ProgressBar` semantics are not materialized in CanvasKit. Confidence: 0.90
- Android emulator for this project: use the Android CLI (`~/.local/bin/android emulator start medium_phone`), NOT the standard Android SDK (emulator/adb not in PATH). Confidence: 0.90
- audioplayers `AudioPlayer()` constructor is lightweight (no platform calls at construction) — safe to use directly in unit tests without mocking/stubbing. Confidence: 0.80
- When testing on physical devices (iOS and Android), disable Wi-Fi and use cellular data to verify the proxy/tunnel chain works under real-world network conditions (catches CDN bot detection, DNS, and firewall issues that don't appear on trusted LAN). Confidence: 0.85
- Before deploying to a physical device (iOS or Android) for cellular testing, pre-verify the backend with curl (resolve endpoint + stream endpoint) to warm the cache and isolate backend issues from mobile-app issues before the first physical playback attempt. Confidence: 0.85
- When testing streaming endpoints with a Range header fix, test bidirectionally: (a) without Range header — should force `Range: bytes=0-` to the upstream CDN and return HTTP 206, and (b) with `Range: bytes=0-1` probe request — should return HTTP 206 with `Content-Range`. This confirms the fix handles both initial requests and seek/probe requests. Confidence: 0.75
- When testing Flutter apps on physical iOS devices and client-side `debugPrint` logs are needed, use `--profile` build mode instead of `--release` — `debugPrint` is a no-op in release builds, so client diagnostics (e.g., `[ApiService]`, `[PlayerProvider]` messages) are invisible without profile mode. Confidence: 0.90
- When `flutter run --release` on a physical iOS device hangs or fails during the Xcode build phase (no app installed, no build output despite `xcodebuild`/`SWBBuild` processes running), fall back to a two-step workflow: build separately with `flutter build ios --release --dart-define=BASE_URL=<url>`, then install with `flutter install -d <deviceId>`. Confidence: 0.75
- When `pumpAndSettle()` hangs indefinitely in Flutter integration tests during active audio playback (because the audio player keeps the widget tree active), kill the stuck test and retry with a test file that has better timeout handling (e.g., `playback_test.dart` over `app_test.dart`). Confidence: 0.75
- The `An animation is still running even after the widget tree was disposed` exception in `audioplayers/src/position_updater.dart` is a known non-fatal cleanup issue during active playback — verify actual playback success (playing=true, position advancing) independently of the test framework's pass/fail status. Confidence: 0.80
- Verify LRU cache memory stability under load by running `ps -o pid,rss,vsz,comm -p $(pgrep -f "tsx src/server.ts")` before and after batch requests — stable RSS/VSZ confirms no memory leaks from caching. Confidence: 0.80
- When a wireless iOS device disconnects during Flutter operations or tests, diagnose reconnection with `idevice_id -l` and `idevicepair list`, then re-establish the connection using `flutter devices --device-timeout 60`. Confidence: 0.75
- When running Flutter integration tests on a physical iOS device for the first time, the device may display a "Trust This Computer" dialog requiring manual interaction before the Dart VM Service can be discovered. If tests fail with "Dart VM Service was not discovered", confirm the trust dialog on the device, then retry — do not attempt to work around it programmatically. Confidence: 0.90
- Before running Playwright E2E tests against a Flutter web target served statically by the backend at `/`, run `flutter build web` first so the backend has the compiled web assets to serve — the web build is a prerequisite, not optional, when the backend serves the app. Confidence: 0.80
- When Flutter web (CanvasKit) `flt-semantics` buttons lack accessible `aria-label`s (common for `IconButton` without explicit tooltips/labels), fall back to geometric + role + tabindex heuristics: find `flt-semantics[role="button"][tabindex="0"]` with a small bounding box (<100×100) in the expected screen region (e.g., bottom-right for player bar controls). Confidence: 0.80
- For debugging Flutter web audio playback when no `<audio>` element is visible in the DOM (because `audioplayers` web 5.3.0 creates detached/temporary audio elements managed via Web Audio API), instrument browser APIs (`HTMLAudioElement.prototype.play/pause/load`, `AudioContext.prototype.resume`) via Playwright's `addInitScript` before page load to trace whether the Flutter audio player is actually invoking browser audio APIs. Confidence: 0.85
- For quick bug investigation in Flutter web E2E: write targeted debug tests with verbose `[debug]` console logging (DOM state, semantics nodes, network requests, media element state), refine selectors iteratively until root cause is isolated, then convert the debug test into a proper assertion-based verification test. Confidence: 0.75
- When planning optimizations, first run side-by-side comparative A/B tests between different configurations/approaches (e.g., tunnel vs local network) to establish baselines and identify differences — use the comparative results as the empirical starting point for optimization decisions rather than optimizing based on assumptions. Confidence: 0.85
- For comparative testing sessions, create a structured living document that serves dual purpose: (a) a procedural guide for running tests in each configuration, and (b) a persistent repository for results and conclusions that carries forward across sessions — include testing procedures per mode, metrics to collect, hypotheses, and accumulating results/conclusions. Confidence: 0.85
- When running Playwright E2E tests that may run against either a local backend or a Cloudflare Tunnel endpoint, make timeouts environment-aware: detect tunnel mode via `process.env.BASE_URL?.includes('trycloudflare.com')` and scale page-load waits (e.g., 3s→15s), search-result waits (30s→60s), and overall test timeout (default→180s) accordingly — the free Cloudflare Tunnel adds significant latency to asset loading and API calls that causes local-mode timeouts to fail. Confidence: 0.85
- When documenting iterative bug fixes in comparative test docs, include "Iteration notes" showing the progression of attempts — first attempt, why it partially failed (e.g., "started from beginning"), and the refined approach that succeeded — so future sessions understand the reasoning behind the final solution without rediscovering dead-end approaches. Confidence: 0.80
