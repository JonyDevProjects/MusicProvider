# testing-strategy
- When documenting completed testing/validation sessions, write a structured markdown report in `/docs/testing/` — include environment configuration, optimization results with evidence (logs/timings), an end-to-end user flow log, a validation checklist table, quick diagnostic commands, and technical notes (e.g., tunnel URLs, build mode caveats). Confidence: 0.85
- For Flutter multiplatform E2E tests: use the official `integration_test` package (not flutter driver) for iOS and Android, plus Playwright for the web target. Confidence: 0.90
- For Flutter web (CanvasKit) E2E with Playwright: verify values via `aria-label` on semantic nodes (`flt-semantics`), not via DOM text; expose durations on search results (`TrackResult-*`) since `ProgressBar` semantics are not materialized in CanvasKit. Confidence: 0.90
- Android emulator for this project: use the Android CLI (`~/.local/bin/android emulator start medium_phone`), NOT the standard Android SDK (emulator/adb not in PATH). Confidence: 0.90
- audioplayers `AudioPlayer()` constructor is lightweight (no platform calls at construction) — safe to use directly in unit tests without mocking/stubbing. Confidence: 0.80
- When testing on a physical iOS device, disable Wi-Fi and use cellular data to verify the proxy/tunnel chain works under real-world network conditions (catches CDN bot detection, DNS, and firewall issues that don't appear on trusted LAN). Confidence: 0.80
- Before deploying to a physical iOS device for cellular testing, pre-verify the backend with curl (resolve endpoint + stream endpoint) to warm the cache and isolate backend issues from mobile-app issues before the first physical playback attempt. Confidence: 0.80
- When testing streaming endpoints with a Range header fix, test bidirectionally: (a) without Range header — should force `Range: bytes=0-` to the upstream CDN and return HTTP 206, and (b) with `Range: bytes=0-1` probe request — should return HTTP 206 with `Content-Range`. This confirms the fix handles both initial requests and seek/probe requests. Confidence: 0.75
- When testing Flutter apps on physical iOS devices and client-side `debugPrint` logs are needed, use `--profile` build mode instead of `--release` — `debugPrint` is a no-op in release builds, so client diagnostics (e.g., `[ApiService]`, `[PlayerProvider]` messages) are invisible without profile mode. Confidence: 0.90
- Verify LRU cache memory stability under load by running `ps -o pid,rss,vsz,comm -p $(pgrep -f "tsx src/server.ts")` before and after batch requests — stable RSS/VSZ confirms no memory leaks from caching. Confidence: 0.80
- When a wireless iOS device disconnects during Flutter operations or tests, diagnose reconnection with `idevice_id -l` and `idevicepair list`, then re-establish the connection using `flutter devices --device-timeout 60`. Confidence: 0.75
